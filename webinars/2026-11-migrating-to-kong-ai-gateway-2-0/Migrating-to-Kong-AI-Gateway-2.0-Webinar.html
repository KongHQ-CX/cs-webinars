Where most of us are

The AI platform we all built on 3.x

  • One service and route per model or API
  • Each route: its own ai-proxy-advanced, auth and rate limiting
  • The provider credential repeated on every route
  • AI intent spread across many primitives
Most AI traffic on Kong Gateway 3.x grew one route at a time. A team needs Claude: add a route. Someone needs embeddings: another route. It works, but every route carries its own copy of the provider, model, credential and policies.

Today · Kong Gateway 3.16

The current setup: one plugin stack per route

This is what we migrate. Every request passes the global key-auth, gets its tier budget from the consumer group, then hits one of eight routes. Each route has its own ai-proxy-advanced with its own copy of the provider credential: OpenAI three times, Bedrock twice, Vertex three times. Kong AI Gateway 2.x turns this into eight models that share three providers.

Section 2

Why move to Kong AI Gateway 2.x

Two reasons: release cadence, and a configuration model built for AI.

Why now

One codebase, two release trains

The AI Gateway ships on its own cadence, independent of the API Gateway.

What

Two independent release trains

A dedicated AI Gateway runtime: kong/kong-ai-gateway.

Where

Konnect first

Where most customers already run their gateways, with a dedicated AI Gateway control plane.

Why

Move at AI speed

Ship faster, take on bigger runtime changes, and iterate on AI-native UX, with zero risk to API management customers.

The old model coupled every AI concept to Gateway primitives: service, route, plugin. Decoupling lets the AI Gateway move at the pace the AI market demands, without touching your API Gateway upgrade cycle.

What ships

What Kong AI Gateway 2.x brings

A dedicated AI Gateway runtime

A purpose-built data plane, released on its own train.

2

A dedicated entity model, with first-class support for LLMs, MCP servers and agents.

3

Three things: a new runtime, a new UI and entity model in Konnect, and declarative config with kongctl, which is also how today's migration works.

The big idea

From plugins to entities

You no longer assemble services, routes and plugins by hand. You declare the AI resource you want, and the control plane provisions the proxying for you.

AI Gateway v1 · plugin model
  • Build a service and route, then attach a plugin: ai-proxy-advanced, ai-mcp-proxy, ai-a2a-proxy
  • One logical model = a service + route + plugin + supporting plugins
  • AI intent is spread across many primitives
→
AI Gateway v2 · native entity model
  • Declare the AI resource; the control plane wires the proxying
  • First-class entities on a dedicated AI Gateway control plane
  • One entity per logical model, MCP server or agent
  • AI intent lives in one place
This is the mental-model shift: lead with entities, not plugins.

Models + providers

One plugin becomes two reusable entities

v1 · one ai-proxy-advanced plugin
  • Provider, credentials, route type, model options and load balancer, all in one place
  • Credentials inlined per target
  • Reuse means copy and paste across plugins
→
Provider

Upstream connection + credentials. Declared once, referenced by any number of models.

Model

Routing, capabilities, format, balancing, and targets that each reference a provider.

Call it out: route_type splits into a capabilities list + an API formats entry: llm/v1/chat becomes capabilities: [generate] + formats: [openai].

Reuse is the win: declare OpenAI once and reference it from many models. In our demo, eight plugin copies of the credential become one provider per credential.

Section 3

How 3.x maps to 2.x

Now concretely: what each 3.x piece becomes.

Entity mapping

3.x concepts, 2.x entities

Kong Gateway 3.xKong AI Gateway 2.x
route + ai-proxy-advanced targetModel · route paths kept; route.model.values selects on the body model
credential inside each targetModel provider · one per credential, referenced by models
route_type: llm/v1/chatcapabilities: [generate] + formats: [openai]
global key-auth pluginAuth strategy (key-auth) attached to models
consumer + key-auth credentialConsumer + credential, same key
consumer group + scoped ai-rate-limiting-advancedConsumer group + policy

Source: v1 to v2 table, developer.konghq.com/ai-gateway/ai-gateway-v2-concepts

Policies keep the v1 plugin name as type and the plugin config as config, and one policy can be referenced from many entities.

Two client-visible rules

What 2.x expects from a request

1

The route path is a base path

The gateway appends the capability path: /chat/completions, /embeddings, /responses, /v1/messages.

2

The request picks the model

The body model (or the model in the Gemini URL) must match the model's route.model.values.

The converter handles both: paths become base paths, 3.x model names become selectors. But a request without model gets 503 on 2.x, where 3.x used the route's pinned model.

Official SDKs always send model, so most clients are fine. Custom clients that relied on the pinned model must add it: 2.x answers 503 "name resolution failed" (an unknown model is also 503, where 3.x said 400). There is no native default-model setting in 2.3. migration-report.md lists the model each client must send.

One route, before and after

Same intent, platform shape

3.16 · decK 
- name: openai-chat
  paths: [/openai/v1/chat/completions]
  plugins:
    - name: ai-proxy-advanced
      config:
        targets:
          - route_type: llm/v1/chat
            auth:
              header_name: Authorization
              header_value: '${{ env "DECK_OPENAI_AUTH" }}'
            model:
              provider: openai
              name: gpt-5-mini
2.3 · kongctl 
ai_gateway_model_providers:
  - name: openai-1
    type: openai
    config:
      auth:
        headers:
          - name: Authorization
            value: !secret {source: !env DECK_OPENAI_AUTH}
ai_gateway_models:
  - name: openai-chat
    formats: [{type: openai}]
    targets: [{name: gpt-5-mini, provider: openai-1}]
    access: {auth_strategies: [api-key]}
    config:
      route:
        paths: [/openai/v1]
        model: {body_param: model, values: [gpt-5-mini]}
Left: one of eight plugin configs, each with its own credential. Right: the provider is declared once; the model references it. The credential is a write-only secret reference, so no file holds the key.

After · Kong AI Gateway 2.3

After the migration: declared once, referenced everywhere

The same applications, the same keys, the same tiers. Key-auth is now one auth strategy that every model references. The three tiers are three consumer groups pointing to three policies. The eight routes are eight models with no plugins, and the eight copies of the provider credentials are three model providers, one key each. Rotating a provider key is now one change. Room to improve: the converter keeps one model per 3.x route. After the migration, models that share an upstream model can become one model with several capabilities, for example openai-chat and openai-responses as one gpt-5-mini model with generate and agentic. Paths and model names for clients stay the same.

Section 4

The migration, as a repeatable pipeline

Not a one-time manual conversion: a reviewable, repeatable pipeline you can re-run before cutover.

The approach

Six steps from 3.x to 2.x

1

Prepare and export

Tiers in the policies format (3.14+), then deck gateway dump; count routes, plugins, consumers.

2

Convert

kongctl convert ai-gateway with a small config/ folder.

3

Review and fix

Read migration-report.md; apply the fixes on a copy.

4

Plan and apply

kongctl plan --mode apply, then kongctl apply. Never sync shared namespaces.

5

Run in parallel

Same requests and keys against both gateways; compare.

6

Cut over

Switch DNS or the load balancer; keep 3.x warm as the rollback.

kongctl apply is declarative, so the whole pipeline re-runs cleanly: re-plan must say No changes detected.

What the converter needs from you

A small config/ folder

  • gateway.yaml: the target AI Gateway. For an existing gateway, run kongctl adopt ai-gateway once.
  • auth_strategies.yaml: how global auth plugins become strategies. Only one strategy may use models: ['*'].
  • Vault entities only if your vault is a Konnect entity.

Lessons from the field

The converter does most of the work

Routes become models, credentials become providers, consumers keep their keys, and tiers carry over as consumer groups with policies. A report lists what clients must send and anything it couldn't map.

In the demo every route, provider, consumer, key and tier came across. The report is the place to start the review.

Lessons from the field

Review, test, and ask for help when needed

Most items convert as they are. Where something doesn't, a few manual steps may be needed: read migration-report.md, send the same requests to both gateways, and reach out to Kong support or your CSM for anything the converter can't map.

Keep it short here; the runbook in the kit lists the checks we ran, and the Q&A notes in demo.md cover the details if someone asks.

Section 7

Migration checklist

  • Move 3.x tiers to the policies format, with partition_by; test on 3.x
  • Dump every control plane or workspace with AI routes, consumers and groups
  • Write config/: gateway, auth strategies
  • Convert, read migration-report.md, fix on a copy
  • Plan, review, apply to a non-production AI Gateway
  • Same vault access and TLS settings on the 2.x data plane
  • Same test suite on both, including per-consumer budgets and requests without model
  • Tell clients to always send model; agree a cutover window
  • Switch traffic; keep 3.x warm until error rates and usage match
This is also the order of the runbook in the take-home kit.
