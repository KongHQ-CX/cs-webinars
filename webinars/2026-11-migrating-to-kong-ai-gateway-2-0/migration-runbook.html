Kong Gateway 3.x to Kong AI Gateway 2.x: migration runbook

Fill in your settings on the left; every command below updates as you type. You start with two gateways that already run in Konnect: a Kong Gateway 3.x control plane with a data plane, and a Kong AI Gateway 2.x with a data plane. Part 1 loads a typical AI configuration onto the 3.x gateway (OpenAI, Amazon Bedrock, Vertex AI; API keys; token tiers). Part 2 migrates it to the 2.x gateway with deck, kongctl convert ai-gateway and kongctl, and tests both side by side. Settings stay in your browser (secrets are never stored); nothing is sent anywhere.

Step 2Environment variables

Run this once per terminal. kongctl reads the token and API address from KONGCTL_DEFAULT_KONNECT_*; decK takes them as flags. decK also fills the provider credentials and the application API keys into the configuration from DECK_* variables, and kongctl reads the same variables during the migration. The API keys are generated once and kept in secrets/app-keys.env.

mkdir -p «workdir»/secrets && cd «workdir»
export KONNECT_PAT='«patValue»'
export KONNECT_ADDR=https://«region».api.konghq.com
export KONGCTL_DEFAULT_KONNECT_PAT="$KONNECT_PAT"
export KONGCTL_DEFAULT_KONNECT_BASE_URL="$KONNECT_ADDR"
export SRC_CP='«srcCp»' TARGET_GW='«gwName»'
export DECK_KONNECT=(--konnect-token "$KONNECT_PAT" --konnect-addr "$KONNECT_ADDR" --konnect-control-plane-name "$SRC_CP")

# provider credentials (full header values; the Vertex key as one line of JSON)
# "Bearer " followed by your OpenAI API key
export DECK_OPENAI_AUTH='Bearer __REPLACE_ME__'
# "Bearer " followed by your Amazon Bedrock API key
export DECK_BEDROCK_AUTH='Bearer __REPLACE_ME__'
export DECK_GCP_SA_JSON="$(jq -c . «gcpSaFile»)"
export DECK_GCP_PROJECT='«gcpProject»' DECK_GCP_LOCATION='«gcpLocation»'

# application API keys (generated once, reused on every run)
[ -f secrets/app-keys.env ] || for a in APP_REPORTING APP_CHATBOT APP_BATCH APP_ETL; do
  echo "export DECK_KEY_$a='key-$(openssl rand -hex 16)'"; done > secrets/app-keys.env
chmod 600 secrets/app-keys.env && source secrets/app-keys.env

Single quotes matter: a value with a space or $ breaks an unquoted export. The DECK_KONNECT array needs bash or zsh. A new terminal needs this step again.

Step 4Load the 3.x configuration

The example has 8 routes, each with its own ai-proxy-advanced:
  • OpenAI chat, responses and embeddings
  • Bedrock Claude in OpenAI format, and as native Anthropic Messages
  • Vertex Gemini in OpenAI format, embeddings, and native generateContent
Global key-auth, and four consumers in tiers gold, silver and bronze with ai-rate-limiting-advanced: 50,000, 5,000 and 300 tokens per minute per consumer. The tiers use the policies format (Kong Gateway 3.14+): each rule matches one provider and the consumer, both with partition_by: true, so every consumer has its own budget. Every entity carries the tag aigw-migration, and the file selects on it, so sync only touches these entities and leaves anything else on your control plane alone.

Step 5Export the 3.x configuration

Part 2 starts here; with your own 3.x configuration, start here too. The dump is the converter's only input, and it holds the API keys and provider credentials in clear text (that is how they migrate unchanged): treat 01-dump/ as secret.

Step 6Converter input

Two files in config/, and the AI Gateway handed to kongctl:
  • gateway.yaml describes your existing AI Gateway. Use the same name and display name it has in Konnect.
  • auth_strategies.yaml says how the global key-auth becomes a 2.x auth strategy. Global plugins are not converted on their own, because 2.x authenticates per model. Use the key names from step 5, so clients keep sending the same header.
mkdir -p config
cat > config/gateway.yaml <<'EOF'
_defaults:
  kongctl:
    namespace: «nsPrefix»-23
ai_gateways:
  - ref: «gwName»
    name: «gwName»
    display_name: «gwDisplay»
    description: Migrated from Kong Gateway 3.x control plane «srcCp»
    min_runtime_version: "«minRuntime»"
EOF

cat > config/auth_strategies.yaml <<'EOF'
# The global key-auth plugin becomes one auth strategy on every model.
# Only ONE strategy may use models: ['*']; list model names (= 3.x route names) on any other.
auth_strategies:
  - ref: api-key
    name: api-key
    display_name: API key
    type: key-auth
    config:
      key_names: [apikey, x-api-key, x-goog-api-key]
      hide_credentials: true
      key_in_header: true
      key_in_query: true
    models: ['*']
EOF

# hand the existing AI Gateway to kongctl (once; "already has namespace label" means it is done)
kongctl adopt ai-gateway «gwName» --namespace «nsPrefix»-23

Using an identity provider instead of keys? Declare an openid-connect strategy (issuer, auth_methods: [bearer], audience_required, consumer_groups_claim). The converter drops bearer_token_param_type and display_errors (it validates against the 2.0 schema); add them back after converting. Konnect rejects anonymous on a key-auth strategy.

Check B: per-consumer rate-limit budgets

A rule's counter is keyed by the rule and by the matches marked partition_by: true; nothing else splits it. The example's tiers are already in the policies format with a consumer partition, and the converter copies them 1:1, so there is nothing to fix. Check it:

yq -o=json -I=0 '.ai_gateway_policies[] | select(.type == "ai-rate-limiting-advanced") | {(.name): .config.policies[0].match}' 03-final/policies.yaml

Expected

{"ai-rate-limiting-advanced":[{"key":null,"partition_by":true,"type":"provider","values":["openai"]},{"key":null,"partition_by":true,"type":"«rlaId»","values":null}]}
{"ai-rate-limiting-advanced-2":[...]}
{"ai-rate-limiting-advanced-3":[...]}

Your own 3.x tiers still use the older llm_providers format? Then the converted rules have no consumer partition, so a tier would share one budget. Best: rewrite the tiers on 3.x in the policies format first (3.14+; see config-examples/1-source-3x/kong-316.yaml), test there, then dump and convert. Or add the partitions on the converted copy:

yq -i '(.ai_gateway_policies[] | select(.type == "ai-rate-limiting-advanced") | .config.policies[].match) |=
  (map(select(.type == "provider") |= . + {"partition_by": true}) + [{"type": "«rlaId»", "partition_by": true}])' 03-final/policies.yaml

Credentials: reference them instead of copying them

The example's 3.x config holds the provider credentials inline, so the converter copies them into providers.yaml as plain text. kongctl accepts write-only fields such as provider credentials only as !secret or as a vault reference; with plain text, kongctl plan stops with field /config/auth/headers/0/value is write-only and requires !secret with a deferred source or a vault reference. This command points them at the DECK_* variables from step 2, and as a bonus no file in 03-final/ holds a secret.

Ideal: a vault. If your 3.x config already uses vault references (for example {vault://env/openai-auth}, HashiCorp Vault, AWS Secrets Manager or a Konnect Config Store), the converter keeps them unchanged and this step disappears; the 2.x data plane then needs the same vault backend as the 3.x one. The example uses inline credentials so the gateways need no extra settings.

yq -i '
  with(.ai_gateway_model_providers[] | select(.type == "openai") | .config.auth.headers[0].value; . = {"source": "DECK_OPENAI_AUTH"} | . tag = "!secret" | .source tag = "!env") |
  with(.ai_gateway_model_providers[] | select(.type == "bedrock") | .config.auth.headers[0].value; . = {"source": "DECK_BEDROCK_AUTH"} | . tag = "!secret" | .source tag = "!env") |
  with(.ai_gateway_model_providers[] | select(.type == "gemini") | .config.auth.service_account_json; . = {"source": "DECK_GCP_SA_JSON"} | . tag = "!secret" | .source tag = "!env")' 03-final/providers.yaml
grep -nE 'value:|service_account_json|source:' 03-final/providers.yaml
grep -rlE 'sk-|bedrock-api-key-|PRIVATE KEY' 03-final || echo "no secrets in 03-final"

Step 9Plan and apply

--mode apply creates and updates, never deletes. Never use sync against namespaces other tools or teams share. The terminal needs the DECK_* variables from step 2 and the AIGW_APIKEY_* variables from step 8.

kongctl diff --plan plan.json | less
kongctl apply --plan plan.json --auto-approve

A plan doesn't prove the config works. Konnect rejects some values only at apply, and some problems only show on the data plane: one entity the data plane refuses makes it drop the whole configuration. Always send traffic (step 10).

Provider credentials and API keys are write-only, so a later plan cannot see when they change. After rotating one, update it in Konnect. Also, kongctl does not see an element removed from a policy's match list; after such a change, compare with kongctl get ai-gateway policies --gateway-name «gwName» -o json.

kongctl get ai-gateway nodes --gateway-name "$TARGET_GW" -o json | jq -r '.[] | "\(.hostname) \(.version) \(.config_sync.state)"'

Step 11Check per-consumer budgets

Status codes alone don't prove the tiers behave as before. app-batch and app-etl are both bronze, with 300 tokens per minute each. Use up app-batch's budget, then call once as app-etl:
  • Per-consumer budgets: app-etl gets 200.
  • One shared budget (no consumer partition, see step 8): app-etl gets 429.
Wait 60 seconds after other tests first.
for u in «srcUrl» «dstUrl»; do echo "== $u"
  for i in $(seq 1 12); do
    c=$(curl -s -o /dev/null -w '%{http_code}' $u/openai/v1/chat/completions -H "apikey: $DECK_KEY_APP_BATCH" \
          -H 'Content-Type: application/json' -d '{"model":"gpt-5-mini","messages":[{"role":"user","content":"In three sentences, explain what an API gateway does."}]}')
    echo "app-batch $c"; [ "$c" = 429 ] && break
  done
  curl -s -o /dev/null -w 'app-etl %{http_code}\n' $u/openai/v1/chat/completions -H "apikey: $DECK_KEY_APP_ETL" \
    -H 'Content-Type: application/json' -d '{"model":"gpt-5-mini","messages":[{"role":"user","content":"Reply OK"}]}'
done

Step 12Cut over

  1. Re-plan: kongctl plan --mode apply -f 03-final --output-file plan.json must say "No changes detected".
  2. Tell client owners what changes: the client table from step 7, and the rate-limit header names.
  3. Freeze changes on the 3.x control plane, or re-run steps 5 to 9 just before the switch.
  4. Move traffic: DNS or load balancer from «srcUrl» to «dstUrl»; keep 3.x running.
  5. Watch errors and token usage on both in Konnect analytics; rate-limit counters start fresh on 2.x.
  6. Rollback = point traffic back to the 3.x proxy; nothing on 3.x was changed.

Step 13Clean up (test runs only)

These commands remove what this runbook created, but leave both gateways and their data planes in place. Don't use kongctl delete -f 03-final: that folder contains gateway.yaml, so it would delete the AI Gateway itself.

# 3.x: everything tagged aigw-migration
deck gateway reset "${DECK_KONNECT[@]}" --select-tag aigw-migration --force

# 2.x: the migrated entities (models first, providers last)
GW_ID=$(kongctl get ai-gateways -o json | jq -r --arg n "$TARGET_GW" '.[] | select(.name == $n) | .id')
for k in models consumer-groups consumers policies auth-strategies model-providers; do
  for id in $(curl -s -H "Authorization: Bearer $KONNECT_PAT" "$KONNECT_ADDR/v1/ai-gateways/$GW_ID/$k?page%5Bsize%5D=100" | jq -r '.data[].id'); do
    curl -s -o /dev/null -X DELETE -H "Authorization: Bearer $KONNECT_PAT" "$KONNECT_ADDR/v1/ai-gateways/$GW_ID/$k/$id"
  done; echo "$k removed"
done

The 2.x loop removes every model, provider, policy, consumer group, consumer and auth strategy on that AI Gateway. Use it only on a gateway dedicated to this exercise.
